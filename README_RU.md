# tech-doc-parser

**Локальный двухэтапный конвейер: сложные технические PDF (сканы, таблицы, схемы) → чанки Markdown, готовые для RAG. 100% офлайн — без облака, API-ключей и Docker. Разработан с расчётом на скромный ноутбук.**

> 🇬🇧 English version: [README.md](README.md)

```
PDF ──▶ parse_pdf.py (этап 1) ──▶ ready_data_*.md ──▶ enrich_chunks.py (этап 2) ──▶ chunks_final.md ──▶ ваш RAG
```

## Зачем это нужно

Универсальные парсеры PDF часто не справляются с реальными техническими документами:

- советские сканы со вложенными заголовками таблиц и двумя системами единиц (СИ + МКГСС)
- страницы, где таблицы и схемы существуют только как изображения, без текстового слоя
- современные мануалы, где текст, схемы и таблицы смешаны на одной странице

Этот проект работает иначе: всё, что может дать текстовый слой, берётся дословно; всё, что он не может (таблицы, схемы, битые сканы), читает **локальная визуальная модель**; затем результат **семантически обогащается** для лучшего поиска.

## Возможности

**Этап 1 — парсинг (`parse_pdf.py`)**

- Постраничный роутинг: чистый текстовый слой извлекается дословно; страницы с таблицами / схемами / битым текстом рендерятся и уходят в визуальную модель
- Детекция настоящих таблиц через PyMuPDF `find_tables()`
- Встроенные изображения вырезаются и описываются отдельно
- Независимость от языка: модель отвечает на языке документа
- Анти-галлюцинаторные промты: числа никогда не «исправляются», противоречия помечаются
- Автообрезка повторяющихся артефактов генерации (зацикливаний)
- Постраничное сохранение прогресса; прерванный прогон возобновляется автоматически
- Периодическая выгрузка модели из памяти для очень длинных прогонов

**Этап 2 — обогащение (`enrich_chunks.py`)**

- Нарезка Markdown на семантические чанки (размер настраивается)
- Дедупликация страниц-дубликатов скана
- Карточка обогащения для каждого чанка: суммари, цепочки неисправностей/процессов, параметры с единицами, термины и стандарты, ключевые слова, ссылки «см. также»
- Автоопределение языка каждого чанка (RU / EN промты)
- Повторные попытки при ошибках API; прогресс по чанкам; автовозобновление

## Рассчитано на скромное железо

Проект разработан и протестирован на типичном ноутбуке: **RTX 4060 (8 ГБ VRAM) + 16 ГБ ОЗУ совместно с Windows 11**. Решения для слабых машин:

- Визуальная модель `qwen3.5:9b` по умолчанию занимает ~6,6 ГБ VRAM и уживается с системой; для более слабых GPU в `config.json` переключитесь на `qwen3.5:4b`
- Разрешение рендера по умолчанию — **150 DPI**: практический баланс качества распознавания, скорости и памяти
- Модель периодически выгружается из памяти (`RESET_EVERY` / `UNLOAD_EVERY`), поэтому суммарное число страниц практически не ограничено — ограничено только время
- Один процесс, без Docker, баз данных и лишних сервисов

## Требования

- Windows (`.bat`-скрипты в комплекте; на других ОС запускайте `.py` напрямую)
- Python 3.10+ (при установке — **Add Python to PATH**)
- [Ollama](https://ollama.com)
- Рекомендуется GPU с 8 ГБ+ VRAM (протестировано на ноутбуке RTX 4060 / 16 ГБ ОЗУ). Работа только на CPU возможна, но значительно медленнее.

## Установка

1. Установите Python и Ollama.
2. Запустите `1_install.bat` — он поставит зависимости и скачает модель (один раз).

Эквивалент вручную:

```bash
pip install pymupdf requests
ollama pull qwen3.5:9b
```

## Использование

1. Положите PDF в папку проекта.
2. Запустите `2_parse.bat` → сырой Markdown (`ready_data_*.md`).
3. Запустите `3_enrich.bat` → `chunks_final.md`, итоговый файл для RAG.

Оба этапа работают автономно. При прерывании запустите тот же скрипт снова — обработка продолжится с последней завершённой страницы / чанка.

Загрузите `chunks_final.md` в любую RAG-систему (AnythingLLM, Open WebUI, LangChain и др.).

| Файл | Назначение |
|---|---|
| `parse_pdf.py` | Этап 1: PDF → Markdown |
| `enrich_chunks.py` | Этап 2: Markdown → обогащённые чанки |
| `1_install.bat` | Однократная установка |

## Настройки

Этап 1 читает `config.json`, если он есть (ключи, начинающиеся с `_`, игнорируются). Значения по умолчанию:

| Ключ | По умолчанию | Описание |
|---|---|---|
| `PDF_FILE` | `""` | Обрабатываемый файл; пусто = первый PDF в папке |
| `OUTPUT_FILE` | `rag_ready_data_v3.md` | Выходной файл этапа 1 |
| `PROGRESS_FILE` | `progress_v3.json` | Файл прогресса этапа 1 |
| `MODEL_NAME` | `qwen3.5:9b` | Модель Ollama, общая для обоих этапов. На GPU с <8 ГБ VRAM используйте `qwen3.5:4b` |
| `OLLAMA_URL` | `http://localhost:11434/api/generate` | Адрес API Ollama |
| `CROP_DPI` | `150` | Разрешение рендера. 150 = дефолтный ноутбучный баланс; 200–300 = чётче, но медленнее и тяжелее |
| `MIN_TEXT_CHARS` | `100` | Минимум символов, чтобы считать страницу текстовой |
| `MIN_CYR_RATIO` | `0.4` | Порог детектора мусорного текста (не зависит от языка) |
| `MIN_IMG_W` / `MIN_IMG_H` | `100` / `80` | Минимальный размер вырезаемого изображения |
| `MARGIN` | `10` | Отступ при вырезании, в пунктах |
| `RESET_EVERY` | `50` | Выгружать модель каждые N страниц |

Константы этапа 2 (в начале `enrich_chunks.py`):

| Константа | По умолчанию | Описание |
|---|---|---|
| `CHUNK_MAX_CHARS` | `6000` | Максимум символов в чанке |
| `UNLOAD_EVERY` | `20` | Выгружать модель каждые N чанков (0 = выкл) |
| `MAX_RETRIES` | `2` | Повторные попытки при ошибке API |

## Ограничения

- Модели ≤4B параметров могут ошибаться во вложенных таблицах; при наличии VRAM рекомендуется 9B+
- Очень мелкий шрифт (<6 pt): поднимите `CROP_DPI` до 200–300
- Качество обогащения зависит от размера модели
- На ноутбуках с 8 ГБ VRAM закрывайте другие GPU-ёмкие приложения во время прогона
